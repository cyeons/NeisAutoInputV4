# 행동발달특성 생성 프롬프트 설계안

## 1. 문서의 목적

이 문서는 초등학교 생활기록부의 행동특성 및 종합의견을 생성할 때 사용할 프롬프트의 설계 원칙과 권장 템플릿을 정리한 문서이다. 행동발달특성은 학생에 대한 공식 기록이므로, 자연스러운 문장보다 **사실성, 학생별 매핑 정확성, 비낙인성, 검증 가능성**을 먼저 보장해야 한다.

AI가 교사를 대신해 학생을 평가하도록 만들기보다, 교사가 입력한 관찰 기록을 생활기록부 문체로 정리하는 보조 도구로 한정하는 것이 안전하다. 최종 문장은 반드시 교사가 사실관계와 표현의 적절성을 확인한 뒤 사용해야 한다.

## 2. `docs` 자료 분석 결과

> 참고: 분석에 사용한 외부 자료(`hanegbal1.xlsm`, `hanegbal2.pdf`)는 저작권 문제로 공개 저장소에 포함하지 않았습니다.

### 2.1 `prompt.md`

기존 프롬프트의 장점은 다음과 같다.

- 구체적이고 긍정적이며 신뢰감 있는 문체를 요구함.
- 주어를 생략하고 명사형 종결을 사용하도록 명확히 지시함.
- 줄바꿈, 금지어, 키워드별 문장 분리 등 출력 형태를 제한함.
- 실제 생활기록부와 비슷한 예시를 제공하여 문체 기준을 제시함.

다만 운영용 프롬프트로 사용하기에는 다음 문제가 있다.

- “경력 40년차 교사”라는 역할만으로 정확성이 보장되지는 않음.
- “키워드마다 문장 작성”은 관찰 사실이 부족할 때 AI가 세부 사건을 지어낼 가능성을 높임.
- “한 문장 10~20개 단어”는 한국어에서 단어 수 판정이 모호하고, 제공된 예시의 실제 길이와도 완전히 일치하지 않음.
- “긍정적으로 작성”만 강조하면 개선이 필요한 행동이 사실과 다르게 미화될 수 있음.
- 금지어 목록만으로는 외모, 성별, 가정환경, 건강, 장애, 성격 낙인과 같은 민감한 표현을 충분히 막기 어려움.
- 출력 개수, 학생 순서, 입력에 없는 사실, 중복 문장, 맞춤법을 검사하는 절차가 없음.
- 예시가 길고 강한 문체를 가지므로 모델이 예시 속 구체적인 사건까지 다른 학생에게 복제할 위험이 있음.

### 2.2 `hanegbal1.xlsm`

문장 은행은 다음 9개 영역으로 구성되어 있다.

1. 생활태도
2. 대인관계
3. 자기관리
4. 생활제안
5. 예체능
6. 학습참여태도
7. 과제수행능력
8. 학업성취도
9. 학습제안

확인 가능한 예시 문장은 275개였다. 문장 길이의 중앙값은 약 47자, 띄어쓰기 단위 중앙값은 약 12어절이었고, 275개 중 187개가 10~20어절 범위에 있었다. 따라서 10~20어절은 참고 범위로는 유효하지만 절대 규칙으로 사용하면 자연스러운 문장을 불필요하게 훼손할 수 있다.

빈도가 높은 종결 방식은 `있음`, `학생임`, `함`, `바람직함`, `돋보임`, `필요함`, `참여함`, `기대됨`, `우수함`, `보임` 등이었다. 이를 보면 특정 네 가지 종결형만 허용하기보다 생활기록부에 자연스러운 명사형 종결을 허용하되, 한 문단에서 같은 종결을 반복하지 않도록 하는 편이 좋다.

문장 은행에서 채택할 특징은 다음과 같다.

- 학생을 직접 호명하지 않고 행동과 태도부터 서술함.
- `관찰 가능한 행동 → 드러난 역량 또는 태도` 순으로 작성함.
- 책임감, 배려, 협력, 자기관리, 수업 참여 등 영역을 분명히 함.
- 개선 내용은 현재의 노력, 변화 또는 지원 방향과 함께 표현함.
- 문장을 `~함`, `~음`, `~임`, `~보임`, `~돋보임`, `~기대됨` 등의 명사형으로 끝냄.

반면 문장 은행 전체를 그대로 모범 답안으로 사용해서는 안 된다. 다음과 같은 오래되거나 부적절한 표현이 일부 포함되어 있기 때문이다.

- `어린이`, `아이`, `귀여운`, `착한`, `타의 모범`처럼 평가자의 정서나 가치 판단이 강한 표현
- 성별, 이성·동성 관계, 외모를 불필요하게 언급하는 표현
- `산만함`, `부족함`, `미흡함`처럼 맥락 없이 학생을 고정적으로 규정할 수 있는 표현
- `장애` 등 민감한 단어가 다른 의미의 문맥에 섞인 사례
- 복수 문장이 한 셀에 들어가거나 문장이 잘린 사례
- 띄어쓰기, 오탈자, 중복 문장, `학생임`과 `어린이임`이 혼재하는 사례

따라서 이 자료는 **문체와 영역 분류를 참고하는 자료**로만 사용하고, 문장 자체를 무작위로 복사하거나 전체를 few-shot 예시로 넣지 않는 것이 좋다.

### 2.3 `hanegbal2.pdf`

PDF는 9쪽으로 구성되어 있으며 다음 내용을 폭넓게 다룬다.

- 학습 및 수업 태도, 질문과 발표, 호기심
- 체육, 미술, 음악, 코딩 등 예체능·비교과 활동
- 학급 회의, 1인 1역, 회장단 등 학급 활동
- 생활 습관, 책임감, 예의, 사과, 배려와 존중
- 교우 관계와 다양한 참여 성향
- 학습의 어려움, 흥미 부족, 수업 태도, 고집, 갈등, 지각 등 개선 내용
- 가정에 전달하는 마무리 문구

채택할 수 있는 가장 유용한 방식은 구체적인 장면을 근거로 태도를 설명하는 것이다. 예를 들어 단순히 `책임감이 있음`이라고 쓰기보다 `학급에서 맡은 역할을 꾸준히 수행함`이라는 관찰 사실을 먼저 제시하는 방식이다.

그대로 사용하지 말아야 할 요소도 많다.

- `선생님으로서`, `고맙고 대견함`, `부모님께 부탁드림` 등 교사의 감상이나 가정통신문 문체
- `다른 친구들보다`, `타의 모범`과 같은 불필요한 비교·서열화
- `지루한 교과`, `따끔한 눈총`, `개그 욕심` 등 공식 문서에 부적합한 구어체
- `아이입니다`, `뛰어납니다` 등 서술형 종결과 명사형 종결의 혼재
- 관찰 사실보다 성품을 단정하거나 미래를 과도하게 예측하는 표현
- 부정적 행동 뒤에 무관한 장점을 붙여 사실을 상쇄하는 방식
- 학부모에게 직접 말을 거는 9쪽의 마무리 문구

### 2.4 현재 V4 구조와의 연결

현재 `neis_v4/ai/base.py`의 교과 평어 프롬프트는 다음 장점을 이미 갖고 있다.

- 학생 수와 학생별 문장 수를 명시함.
- 정확한 줄 수를 요구함.
- 명사형 종결을 요구함.
- 이전 결과를 제공하여 반복을 줄이려 함.
- 줄 수가 맞지 않으면 보정 요청을 한 번 수행함.

행동발달특성에서는 여기에 다음 기능이 추가되어야 한다.

- 학생마다 서로 다른 관찰 기록을 구조화하여 전달
- 입력에 없는 사실을 생성하지 못하게 하는 근거 제한
- 학생 순서가 뒤바뀌지 않도록 `row_id` 보존
- 민감정보·낙인·비교·과장 표현 검사
- 문장 수뿐 아니라 종결형, 글자 수, 금지어, 중복률, 사실 추가 여부 검사
- 관찰 근거가 부족한 학생을 억지로 생성하지 않는 실패 처리

## 3. 가장 중요한 설계 원칙

### 3.1 “키워드 확장”이 아니라 “관찰 기록 정리”로 정의

입력을 단순한 성격 키워드로 받으면 모델이 그럴듯한 사건을 만들어 낼 수 있다.

좋지 않은 입력:

```text
배려심, 책임감, 발표를 어려워함
```

권장 입력:

```json
{
  "observations": [
    {
      "area": "대인관계",
      "fact": "모둠 활동에서 의견을 말하지 못한 친구에게 발언 기회를 양보함",
      "frequency": "여러 차례"
    },
    {
      "area": "책임감",
      "fact": "급식 도우미 역할을 정해진 날마다 수행함",
      "frequency": "지속적"
    },
    {
      "area": "의사소통",
      "fact": "전체 발표에서는 목소리가 작지만 모둠 안에서는 자신의 생각을 설명함",
      "change": "학기 초보다 발표 시도가 늘어남"
    }
  ]
}
```

프롬프트에는 “입력의 의미를 자연스럽게 풀어쓰되, 입력에 없는 사건·원인·빈도·기간·역할·관계·성과를 추가하지 말라”고 명시해야 한다.

### 3.2 긍정성보다 사실성을 우선

개선이 필요한 행동을 무조건 장점으로 바꾸면 공식 기록의 신뢰성이 떨어진다. 다음 순서를 지킨다.

1. 관찰된 행동을 중립적으로 표현함.
2. 낙인 대신 특정 상황과 행동을 씀.
3. 실제 입력에 변화나 노력이 있을 때만 이를 덧붙임.
4. 근거가 있을 때만 성장 가능성을 표현함.

예:

```text
나쁨: 산만하지만 마음만 먹으면 크게 발전할 학생임.
권장: 관심 있는 활동에는 집중하여 참여하며, 수업 전반에서 주의를 유지하려는 연습이 필요함.
```

단, 두 번째 문장의 `관심 있는 활동에 집중함`과 `연습이 필요함`도 반드시 교사의 입력에 있어야 한다.

### 3.3 행동과 해석을 구분

문장의 기본 구조는 다음이 좋다.

```text
[구체적 상황 또는 반복 행동] + [그 행동에서 확인되는 태도·역량]
```

예:

```text
모둠 활동에서 친구들의 의견을 끝까지 듣고 공통점을 찾아 정리하는 등 협력적인 의사소통 능력이 돋보임.
```

`배려심이 깊음`, `성품이 착함`처럼 내면을 바로 단정하기보다, 이를 뒷받침하는 행동을 앞에 둔다.

### 3.4 근거가 부족하면 생성하지 않음

공식 기록에서는 빈 문장보다 지어낸 문장이 더 위험하다. 다음 중 하나에 해당하면 정상 문장을 생성하지 않고 검토 상태를 반환하는 것이 좋다.

- 관찰 기록이 비어 있음.
- `좋음`, `보통`, `문제 있음`처럼 의미가 지나치게 추상적임.
- 서로 모순되는 기록이 있으나 시점이나 상황이 구분되지 않음.
- 민감정보만 있고 학교생활의 관찰 행동이 없음.
- 개선되었다고 쓰라는 요청은 있으나 변화의 근거가 없음.

권장 상태값:

```json
{"row_id":"S003","status":"needs_review","reason":"구체적인 관찰 행동이 부족함","comment":""}
```

이 상태값은 생활기록부 입력 표로 자동 전송하지 않아야 한다.

### 3.5 학생별 매핑을 문장 순서에만 맡기지 않음

여러 학생을 한 번에 생성할 때 한 줄씩 출력하게 하면 줄 누락으로 뒤 학생의 문장이 잘못 배정될 수 있다. 각 학생에게 화면의 행 번호와 연결되는 익명 `row_id`를 부여하고, 모델이 같은 값을 반환하게 해야 한다.

학생 이름은 문장 생성에 필요하지 않으므로 가능하면 모델에 보내지 않는다. 필요한 경우에도 프롬프트 안에서 이름을 문장에 쓰지 말라고 명시한다.

### 3.6 생성과 검증을 분리

한 번의 프롬프트에 모든 책임을 맡기지 말고 다음 순서로 처리한다.

1. 입력 데이터 사전 검사
2. 초안 생성
3. 프로그램 규칙 검사
4. 실패 항목만 보정
5. 교사 검토
6. 확정된 문장만 NEIS 입력 표로 이동

## 4. 권장 입력 데이터 구조

```json
{
  "task": "behavior_development_comment",
  "school_level": "elementary",
  "semester": "2026-1",
  "options": {
    "sentence_count_min": 2,
    "sentence_count_max": 4,
    "target_chars_min": 100,
    "target_chars_max": 250
  },
  "students": [
    {
      "row_id": "S001",
      "grade": 4,
      "observations": [
        {
          "area": "책임감",
          "fact": "학급 도서 정리 역할을 정해진 날마다 수행함",
          "frequency": "지속적",
          "period": "1학기"
        },
        {
          "area": "대인관계",
          "fact": "모둠원 사이에 의견 차이가 있을 때 각 의견을 차례로 듣고 공통점을 정리함",
          "frequency": "여러 차례"
        },
        {
          "area": "의사소통",
          "fact": "전체 발표에서 목소리가 작은 편임",
          "change": "학기 초보다 자발적으로 발표하는 횟수가 늘어남"
        }
      ],
      "teacher_note": "책임감과 협력 태도를 중심으로 작성"
    }
  ]
}
```

### 입력 필드 작성 원칙

- `fact`: 실제로 관찰한 행동만 기록한다.
- `frequency`: `한 차례`, `여러 차례`, `지속적`처럼 확인 가능한 경우에만 적는다.
- `period`: 실제 기간이 중요할 때만 적는다.
- `change`: 이전과 이후가 모두 관찰되었을 때만 적는다.
- `area`: 프로그램에서 미리 정의한 분류값을 사용한다.
- `teacher_note`: 강조 순서나 제외 요청만 적고, 새로운 사실을 대신하지 않는다.
- 이름, 주민번호, 연락처, 가정형편 등 생성에 필요 없는 개인정보는 전송하지 않는다.

권장 행동 영역은 자료의 분류를 현대적으로 다듬어 다음처럼 구성할 수 있다.

- 기본생활 및 자기관리
- 책임감 및 역할 수행
- 공동체 참여 및 협력
- 배려 및 존중
- 의사소통 및 갈등 조정
- 자기주도성 및 도전
- 학습 참여 태도
- 예술·체육 및 관심 분야
- 변화와 성장
- 추가 지원 또는 연습이 필요한 부분

---

## 5. 권장 시스템 프롬프트

아래 내용은 OpenAI의 `instructions` 또는 Gemini 요청의 고정 프롬프트 영역에 두는 것이 좋다. 사용자가 입력하는 관찰 자료보다 항상 우선하도록 분리한다.

```text
당신은 대한민국 초등학교 교사가 제공한 관찰 기록을 행동특성 및 종합의견 문체로 정리하는 기록 작성 보조자이다.

이 문장은 공식 학교생활기록 자료의 초안이다. 문장의 화려함보다 사실성, 중립성, 학생의 존엄성, 입력 자료와의 일치가 우선한다.

[사실성 원칙]
1. 제공된 관찰 기록에 명시된 사실만 사용한다.
2. 입력에 없는 사건, 역할, 기간, 빈도, 원인, 의도, 관계, 성과, 감정, 성격, 진단, 미래 결과를 추측하거나 추가하지 않는다.
3. 관찰 행동을 자연스럽게 요약할 수는 있지만 의미를 확대하거나 축소하지 않는다.
4. 변화와 향상은 전후 변화가 입력에 명시된 경우에만 쓴다.
5. 성장 가능성은 이를 뒷받침하는 현재의 노력이나 변화가 입력에 있을 때만 쓴다.
6. 근거가 부족하거나 기록이 모순되면 문장을 지어내지 말고 needs_review 상태를 반환한다.

[표현 원칙]
1. 학생의 이름과 '이 학생은', '학생은', '그는', '그가', '그의' 같은 주어를 쓰지 않는다.
2. 구체적인 관찰 행동을 먼저 제시하고 그 행동에서 확인되는 태도나 역량을 연결한다.
3. 모든 문장은 '~함', '~음', '~임', '~보임', '~돋보임', '~갖춤', '~기대됨', '~필요함' 등 자연스러운 명사형으로 끝낸다.
4. 간결하고 명확한 공적 문체를 사용하며 구어체, 감탄, 교사의 개인 감상, 학부모에게 하는 말을 쓰지 않는다.
5. 개선이 필요한 내용은 특정 상황의 관찰 행동으로 중립적으로 쓰고, 학생 전체를 고정적으로 규정하지 않는다.
6. 서로 관련 없는 장점을 붙여 개선 내용을 억지로 상쇄하지 않는다.
7. 같은 뜻, 문장 구조, 종결어를 불필요하게 반복하지 않는다.
8. 입력에 하나의 단어만 있더라도 구체적인 사례를 창작하지 않는다.

[금지 내용]
1. 질병, 장애, 심리 상태, 지능, 가정환경, 경제상황, 종교, 인종·민족, 외모, 신체 특징, 성별에 관한 불필요한 언급
2. 다른 학생과의 서열 비교 또는 우열 단정
3. '모범생', '문제아', '장애우', '어린이', '아이', '착한', '귀여운', '평범한', '정상적인', '타의 모범' 등 낙인·정서·상투적 평가 표현
4. '산만한 학생', '이기적임', '게으름', '고집이 셈'처럼 사람 자체를 규정하는 표현
5. '선생님으로서', '대견함', '고맙게 여겨짐', '부모님께 부탁드림' 같은 교사 감상 또는 가정통신문 표현
6. 입력에 없는 날짜, 직책, 수상, 점수, 교과 성취, 친구 관계

[출력 원칙]
1. 입력된 row_id마다 정확히 하나의 JSON 객체를 JSONL 형식으로 출력한다.
2. 입력과 동일한 순서와 row_id를 유지하며 누락, 병합, 추가하지 않는다.
3. 정상 생성은 status를 ok로 하고 comment에 완성 문단을 넣는다.
4. 근거 부족 또는 모순은 status를 needs_review로 하고 comment는 빈 문자열로 둔다.
5. comment 안에는 줄바꿈, 번호, 불릿, 제목, 마크다운, 따옴표 설명을 넣지 않는다.
6. JSONL 이외의 설명을 출력하지 않는다.
```

## 6. 권장 사용자 프롬프트 템플릿

```text
# 작업
아래 학생별 관찰 기록을 바탕으로 행동특성 및 종합의견 초안을 작성하라.

# 이번 요청의 출력 조건
- 학생 수: {{student_count}}명
- 학생당 문장 수: {{sentence_count_min}}~{{sentence_count_max}}문장
- 학생당 권장 길이: {{target_chars_min}}~{{target_chars_max}}자
- 한 문단 안에서 줄바꿈 금지
- 각 관찰 기록의 핵심을 빠뜨리지 않되 동일한 내용을 반복하지 않기
- 여러 관찰 내용을 중요도와 관련성에 따라 자연스럽게 묶기
- teacher_note는 강조 방향일 뿐 새로운 사실의 근거로 사용하지 않기

# 학생별 관찰 기록
{{students_json}}

# 출력 전 내부 점검
각 결과에 대해 다음을 조용히 점검한 뒤 최종 JSONL만 출력하라.
1. 입력에 없는 사실을 추가하지 않았는가?
2. row_id와 학생 순서가 정확한가?
3. 모든 문장이 명사형으로 끝나는가?
4. 금지 내용과 낙인 표현이 없는가?
5. 관찰 행동보다 성격을 과도하게 단정하지 않았는가?
6. 문장 수와 글자 수 범위에 맞는가?
7. 다른 학생의 결과와 핵심 구절이 지나치게 겹치지 않는가?
```

### 출력 예

```jsonl
{"row_id":"S001","status":"ok","reason":"","comment":"학급 도서 정리 역할을 정해진 날마다 꾸준히 수행하여 맡은 일에 대한 책임감이 돋보임. 모둠원 사이에 의견 차이가 있을 때 각 의견을 차례로 듣고 공통점을 정리하는 등 협력적인 의사소통 능력을 보임. 전체 발표에서는 목소리가 작은 편이나 학기 초보다 자발적으로 발표하는 횟수가 늘어 자신의 생각을 표현하려는 노력이 돋보임."}
{"row_id":"S002","status":"needs_review","reason":"구체적인 관찰 행동이 부족함","comment":""}
```

JSONL을 현재 프로그램 구조에 바로 적용하기 어렵다면 임시로 `row_id<TAB>comment` 형식을 사용할 수 있다. 그러나 공식 자료에서 줄 누락에 따른 오배정을 막으려면 장기적으로는 JSONL과 `row_id` 검증을 권장한다.

## 7. 좋은 문장을 만드는 세부 규칙

### 7.1 문장 수와 길이

기존 Excel 예시는 대체로 10~20어절에 많이 분포하지만 예외도 적지 않다. 한국어는 조사와 복합어 때문에 어절 수만 강제하면 부자연스러운 문장이 되기 쉽다.

권장 기준:

- 문장당 약 35~80자
- 학생당 2~4문장
- 전체 글자 수는 UI에서 설정 가능하게 함
- 최대 글자 수를 넘으면 덜 중요한 수식어와 중복 내용을 먼저 제거함
- 억지로 한 문장을 늘이거나 둘로 쪼개지 않음

실제 NEIS 입력란의 허용 길이를 프로그램에서 확인한 뒤 `target_chars_max`를 설정값으로 관리하는 것이 좋다.

### 7.2 종결형

허용 예:

- 책임감 있게 수행함.
- 협력적인 태도가 돋보임.
- 자신의 의견을 논리적으로 설명할 수 있음.
- 꾸준히 실천하는 자세를 갖춤.
- 참여하려는 노력이 엿보임.
- 주의를 유지하는 연습이 필요함.

피해야 할 예:

- 수행합니다.
- 수행했다.
- 수행하는 것 같다.
- 정말 대견하고 고맙습니다.
- 훌륭한 어린이임.

문단 내 종결형을 다양하게 쓰되, 다양성을 위해 의미가 어색한 종결어를 억지로 사용하지 않는다.

### 7.3 개선 내용 작성

개선 내용은 다음 세 요소 중 입력에 존재하는 것만 사용한다.

```text
[구체적인 상황] + [현재 보이는 행동] + [실제 관찰된 노력·변화 또는 필요한 연습]
```

예:

```text
입력: 전체 발표에서 목소리가 작음. 모둠 발표에는 참여함. 학기 초보다 발표 시도가 늘었음.
출력: 전체 발표에서는 목소리가 작은 편이나 모둠 발표에 꾸준히 참여하며, 학기 초보다 발표 시도가 늘어 자신의 생각을 표현하려는 노력이 돋보임.
```

피해야 할 방식:

- `마음만 먹으면`, `조금만 노력하면`처럼 근거 없이 의지를 판단함.
- `산만하지만 착함`처럼 관련 없는 장점으로 부정적 행동을 덮음.
- `앞으로 크게 발전할 것임`처럼 미래를 단정함.
- `부족함`, `미흡함`만 남겨 고정적인 인상을 줌.

### 7.4 비교 표현

다른 학생과의 비교는 원칙적으로 쓰지 않는다.

```text
피함: 또래보다 집중력이 뛰어남.
권장: 수업 내용을 끝까지 경청하고 주어진 활동에 집중하여 참여함.
```

객관적 기록에 비교가 반드시 필요한 특별한 경우에도 모델이 임의로 비교 대상을 만들지 못하게 해야 한다.

### 7.5 예시 자료 사용법

긴 예시를 많이 넣으면 모델이 학생별 차이보다 예시 표현을 복사할 수 있다. 영역별로 다음 조건을 만족하는 1~2개 예시만 선택하는 것이 좋다.

- 관찰 행동이 먼저 나옴.
- 입력과 출력의 대응 관계가 분명함.
- 민감하거나 오래된 표현이 없음.
- 교사의 감상이나 학생 간 비교가 없음.
- 명사형 종결이 정확함.
- 서로 다른 문장 구조를 보여 줌.

가능하면 단순 완성문 예시보다 `관찰 입력 → 허용 출력` 쌍을 제공한다. 또한 잘못된 예시와 그 이유를 한두 개 포함하면 금지 규칙을 더 안정적으로 적용할 수 있다.

## 8. 프롬프트만으로 해결하지 말아야 할 검증

모델에게 “반드시 지켜라”라고 쓰는 것만으로는 충분하지 않다. 다음 항목은 프로그램 코드에서 검사해야 한다.

### 8.1 구조 검사

- 결과 수가 요청한 학생 수와 같은지
- 모든 `row_id`가 입력과 일치하는지
- 중복, 누락, 알 수 없는 `row_id`가 없는지
- `status`가 허용값인지
- `needs_review`의 `comment`가 비어 있는지
- JSON 파싱에 성공하는지

### 8.2 문체 검사

- 줄바꿈, 번호, 불릿, 마크다운이 없는지
- 모든 문장의 마지막이 허용 명사형인지
- 서술형 종결인 `합니다`, `입니다`, `됩니다`가 남지 않았는지
- 이름, `이 학생은`, `그는`, `그의` 같은 주어가 없는지
- 글자 수와 문장 수가 설정 범위인지

### 8.3 안전 표현 검사

금지어는 한 목록으로 끝내지 말고 범주별로 관리한다.

- 인칭·호칭: `어린이`, `아이`, `그는`, `그의`, `학생은`
- 낙인·단정: `문제아`, `게으름`, `이기적`, `정상`, `비정상`
- 감상·상투어: `대견함`, `고맙게`, `착한`, `귀여운`, `타의 모범`
- 비교·서열: `다른 친구보다`, `또래보다`, `가장`, `최고`
- 민감 범주: 건강, 장애, 심리, 가족, 경제, 종교, 인종, 외모, 성별 관련 용어

민감 단어는 문맥에 따라 정상적으로 사용될 수도 있으므로 단순 삭제보다 “자동 입력 차단 후 교사 확인”이 적절하다.

### 8.4 사실 일치 검사

완전 자동 판정은 어렵지만 다음은 확인할 수 있다.

- 입력에 없는 날짜, 숫자, 직책, 교과명, 행사명이 출력에 새로 생겼는지
- 입력에 없는 `항상`, `매번`, `모든`, `전 교과`, `여러 차례` 같은 빈도·범위 표현이 생겼는지
- 입력에 없는 `향상됨`, `개선됨`, `극복함` 같은 변화 표현이 생겼는지
- 개선이 필요한 관찰이 장점으로 반전되거나 누락되지 않았는지

### 8.5 중복 검사

- 같은 학생 안에서 의미가 중복되는 문장이 없는지
- 학생 간 완전히 동일한 문장이 없는지
- 최근 결과와 긴 공통 구절이 반복되지 않는지
- 종결어 하나만 바꾼 사실상 동일한 문장이 없는지

단순 문자열 일치뿐 아니라 형태소를 제거한 핵심 어절의 n-gram 유사도나 문장 임베딩을 이용할 수 있다. 다만 중복을 피하려고 입력에 없는 표현을 추가해서는 안 된다.

## 9. 보정 프롬프트

전체를 다시 생성하면 정상 문장까지 바뀔 수 있으므로 실패한 행만 보정하는 것이 좋다.

```text
다음 결과는 행동특성 및 종합의견 자동 검사에서 실패하였다.
원래 관찰 기록과 실패한 결과를 비교하여 해당 row_id만 수정하라.

[절대 조건]
- 원래 관찰 기록에 없는 사실을 추가하지 않는다.
- 정상 판정을 받은 다른 row_id의 문장은 변경하거나 출력하지 않는다.
- 실패 사유만 바로잡는다.
- 근거 부족이나 모순은 억지로 고치지 말고 needs_review로 반환한다.
- 시스템 프롬프트의 사실성, 표현, 금지 내용, JSONL 출력 원칙을 모두 따른다.

[실패 항목]
{{failed_items_json}}

[검사 실패 사유]
{{validation_errors_json}}

JSONL만 출력하라.
```

보정은 한 번 또는 제한된 횟수만 수행하고, 같은 항목이 다시 실패하면 교사 검토 대상으로 넘긴다.

---

## 10. 권장 생성 설정

현재 Gemini 생성 설정의 `temperature=0.8`, `top_p=0.9`는 표현 다양성에는 유리하지만 공식 기록 초안에는 변동성이 큰 편이다.

권장 방향:

- 초안 생성 temperature: 약 `0.2~0.5`
- 보정 생성 temperature: 약 `0~0.2`
- 모델이 지원하면 JSON schema 또는 structured output 사용
- 학생 수가 많으면 작은 묶음으로 나누되 `row_id`를 유지
- 다양성은 높은 temperature보다 관찰 자료의 구체성, 문장 구조 슬롯, 최근 출력 중복 검사로 확보
- 모델과 공급자가 달라도 동일한 검증기를 통과하게 함

정확한 값은 대표 관찰 자료로 평가 세트를 만든 뒤 모델별로 조정한다.

## 11. 품질 평가용 테스트 세트

프롬프트를 실제 기능에 적용하기 전에 최소한 다음 사례를 포함한 고정 테스트 세트를 만드는 것이 좋다.

1. 장점만 있는 학생
2. 장점과 개선 내용이 함께 있는 학생
3. 같은 행동이 상황에 따라 다르게 나타나는 학생
4. 학기 중 변화가 명확한 학생
5. 관찰 기록이 한 개뿐인 학생
6. `성실함`, `착함`처럼 추상 키워드만 있는 학생
7. 서로 모순되는 관찰 기록이 있는 학생
8. 민감정보가 포함된 입력
9. 날짜, 직책, 행사명이 실제로 입력된 학생
10. 여러 학생의 관찰 내용이 매우 비슷한 묶음
11. 긴 관찰 기록과 최대 글자 수 제한이 있는 학생
12. 빈 입력 또는 잘린 입력

각 결과를 다음 항목으로 평가한다.

- 입력 사실 보존
- 입력에 없는 사실의 추가 여부
- 학생별 매핑 정확성
- 공적 문체와 명사형 종결
- 구체성
- 비낙인성
- 개선 내용의 중립성
- 학생 간 중복도
- 맞춤법과 띄어쓰기
- 교사가 수정 없이 채택할 수 있는 비율

## 12. 권장 운영 흐름

```text
교사의 관찰 기록 입력
→ 필수 필드·민감정보 사전 검사
→ 익명 row_id로 생성 요청
→ 구조화된 JSONL 수신
→ 구조·문체·금지어·중복·사실 추가 검사
→ 실패 행만 1회 보정
→ 교사 검토 화면에서 원 관찰 기록과 초안을 나란히 표시
→ 교사가 수정·승인
→ 승인된 문장만 NEIS 입력 표로 이동
```

검토 화면에서는 각 문장이 어떤 관찰 기록을 사용했는지 확인할 수 있게 하는 것이 좋다. 생성 버튼을 누른 즉시 기존 학생 내용에 덮어쓰지 말고, 초안과 확정 상태를 구분해야 한다.

## 13. 최종 권고

행동발달특성 프롬프트의 핵심은 “노련한 교사처럼 써라”가 아니라 다음 네 가지를 명시적으로 보장하는 데 있다.

1. **관찰 근거 밖으로 나가지 않음**
2. **학생을 낙인찍지 않고 행동을 기록함**
3. **학생별 결과의 순서와 식별자를 보존함**
4. **생성 결과를 코드와 교사가 이중 검증함**

`prompt.md`, Excel 문장 은행, PDF 예시의 장점인 구체성·명사형 종결·성장 중심 문체는 유지하되, 오래된 호칭, 비교, 감상, 과장, 근거 없는 긍정화는 제거해야 한다. 이 원칙을 시스템 프롬프트, 구조화된 입력, 자동 검증, 교사 승인 절차에 각각 나누어 구현하는 것이 가장 안정적이다.
